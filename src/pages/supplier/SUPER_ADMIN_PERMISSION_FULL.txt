Super-admin Permission System — Full Functionality & UI/UX (No-code)

OVERVIEW
- Super-admin manually creates users (id/password) and assigns page/module permissions via a checkbox matrix.
- UI shows only allowed pages and features to the logged-in user; everything else is hidden or disabled.
- Implementation context: Electron desktop app + IndexedDB for local storage.
- Electron main process handles secure operations: password hashing, file encrypt/upload (rclone), IPC for privileged actions.
- Renderer (UI) reads IndexedDB and renders permitted pages; it communicates with main via secure IPC.

KEY CONCEPTS (No-code)
1. User: {id, username, displayName, active}
2. Permission: {code, label, module}
3. Role (optional): grouped permission presets
4. UserPermission: mapping userId ⇄ permissionCode (boolean)
5. PageCatalog: list of pages/modules with default permission codes
6. AuditLog: who changed what and when

USER FLOWS (No-code)
A. Create User
- Super-admin opens "User Management" > "Create User".
- Form fields: username, displayName, temporary password, role (optional), active toggle.
- On save: main process hashes password and stores user record in IndexedDB.
- After creation, auto-open Permission Matrix for that user.

B. Permission Matrix (per user)
- Grid: rows = pages/modules; columns = actions (VIEW, CREATE, EDIT, DELETE, POST, APPROVE, EXPORT).
- Checkboxes: tick to grant, untick to revoke.
- Controls: Save, Apply Role Defaults, Copy Permissions from another user, Reset to Defaults.
- Save writes UserPermission entries to IndexedDB and writes AuditLog entry.

C. Login & UI Rendering
- User logs in via login screen (renderer sends credentials to main via IPC).
- Main validates password (bcrypt) and returns session token and permission list.
- Renderer reads permission list and PageCatalog from IndexedDB.
- Menu and routes are built dynamically: only pages with PAGE_VIEW permission included.
- Buttons and actions check respective permission codes before rendering/enabling.
- Any privileged action triggers an IPC check in main for extra validation before performing server-like tasks (e.g., exporting, file access, backup).

D. Permission Change Propagation
- When super-admin updates permissions:
  - Save to IndexedDB.
  - Optionally notify active session (if same user logged in) to update UI or force re-login to refresh permissions.
  - Write AuditLog.

UI COMPONENTS (No-code)
1. User Management Page
   - List users with search and role filter.
   - Create / Edit / Delete actions (delete only by super-admin).
   - Quick action: "Open Permission Matrix" per user.

2. Permission Matrix Modal/Page
   - Left column: Module groups (collapsible).
   - Top header: action columns (VIEW, CREATE,...).
   - Master toggles: per-module "All View", "All Edit".
   - Tooltips on each permission explaining effect.
   - Save / Cancel / Apply Role / Copy From User buttons.

3. App Shell (Header + Sidebar + Content)
   - Sidebar menu generated from permissions. Only shows modules where user has PAGE_VIEW.
   - Header shows current user, quick switch user (if allowed), and "Preview as" (super-admin feature).
   - Content area loads pages via router; route guards check permissions.

4. Inline Action Controls
   - Buttons (e.g., "Create Invoice") visible only if user has INVOICE_CREATE.
   - Contextual menus and row actions follow same rules.

5. Audit & Logs Page (Admin)
   - List of permission changes: who, when, what changed.
   - Filters by user/date/action.

UX RULES (No-code)
- Hidden vs Disabled:
  - Menu and entire pages: hide if user lacks PAGE_VIEW.
  - Buttons/forms inside a page: disable or hide based on specific permissions—prefer hide for actions that should not appear at all.
- Feedback:
  - On permission denied, show a friendly message (e.g., "You don't have permission to perform this action. Contact your admin.").
  - On Save permissions, show a summary of changes and option to notify affected users.
- Performance:
  - Cache permissions in memory on login for fast checks; invalidate cache on permission updates.
- Discoverability:
  - Super-admin can preview UI as another user to verify permission effects.
- Accessibility:
  - Keyboard navigable matrix, labels for checkboxes, high contrast for selected states.

DATA & STORAGE (No-code)
- IndexedDB stores: users, permissions, roles, user_permissions, page_catalog, audit_logs.
- Password hashing: performed in main process using bcrypt (renderer never stores raw passwords).
- Session: store token in memory; optionally store session metadata in IndexedDB (do not store password).
- Export/import: main handles exporting selected stores as encrypted file (GPG/AES) and can upload via rclone.

SECURITY & ENFORCEMENT (No-code)
- Electron hardening:
  - nodeIntegration = false; contextIsolation = true.
  - Use secure IPC channels, whitelist handlers.
- Main performs all sensitive operations (hashing, file I/O, rclone).
- Renderer only responsible for UI and reading IndexedDB.
- Backend-like checks:
  - Even if UI hides actions, main enforces permission on IPC calls and denies unauthorized operations.
- Audit trail:
  - Log all permission changes and user creations with timestamps and actor id.

EDGE CASES (No-code)
- Super-admin denies own PAGE_VIEW → warn and require confirmation.
- Role defaults changed → notify users whose permissions changed by role update.
- Offline behavior: IndexedDB works offline; syncing/export must be manual trigger.
- Race conditions: when two admins edit same user's permissions, last-write-wins; show conflict resolution in future enhancements.
